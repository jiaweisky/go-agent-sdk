description: Review only the current uncommitted diff (staged, unstaged, untracked).

Review 当前未提交的改动（staged + unstaged + untracked），只评审本次 diff。不要修改代码、不要提交、不要运行会改变工作区的命令。

Focus（可选）：$ARGUMENTS

## 范围

1. 先运行 `git status --short`。
2. 读取 `git diff --cached`（staged）。
3. 读取 `git diff`（unstaged）。
4. 用 `git ls-files --others --exclude-standard` 找出 untracked 文件，并读取其完整内容。
5. 只评审这些改动及其直接影响；发现无关的既有问题时标注“既有”，不要把它算作本次引入。
6. 如果改动跨 package，检查直接调用方/被调用方是否同步；不要扩散到无关历史代码。

## 评审维度

1. 设计与实现完整性：职责和包边界、校验归属、配置/运行时分离、是否遗漏必要测试或文档。
2. 异常分支：nil/空值、非法枚举、超时/负值、部分失败后的清理、错误上下文、资源释放。
3. 重复代码：逻辑、常量、转换、校验是否应抽取或复用。
4. 函数命名：是否准确表达行为，是否与同包命名一致，是否存在名实不符。
5. 注释与代码一致：注释必须自包含，不引用设计文档编号；改名、改行为后注释是否同步。
6. 重构原则：是否行为保持、是否只做必要改动、是否破坏公开 API/配置兼容、测试是否同步。
7. 可读性与圈复杂度：函数是否过长、分支是否过多；即使复杂度固有，也要评估能否拆成更小的函数。
8. 空行与排版：用空行分隔不同逻辑阶段；空行应体现意图变化，不要机械空行；同类函数保持一致；空行不能替代必要的函数拆分。
9. 验证：根据改动范围运行 `go build`、`go vet`、相关测试、`gofmt` 检查，以及本次改动新增的 lint 问题。

## 输出格式

- 结论：是否可以合并，是否存在 P0/P1。
- 发现：按 P0/P1/P2/P3 排序；每条给出 `file:line`、问题、建议，并标注“本次引入/既有”。
- 若要求修复：列出已改内容并说明未改项及原因。
- 验证结果：列出实际运行的命令和结果；未运行的要说明原因。
