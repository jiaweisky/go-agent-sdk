---
description: Review an existing file, directory, or package without looking at diffs.
---

Review 指定范围的已有代码（不是 diff）。不要修改代码；只做评审。

Target：$ARGUMENTS

如果 Target 为空，先询问用户要评审的文件/目录/包，不要默认扫描整个 repository。

## 范围

- 只评审指定文件/目录/包；需要判断调用关系时，可以查看直接依赖和直接调用方。
- 不把范围外的历史问题混入结论；必须提及时标注“范围外”。
- 不仅看签名，要阅读目标文件及必要的直接依赖，确认实现逻辑。

## 评审维度

1. 设计与实现完整性：职责边界、包依赖、校验归属、配置与运行时是否分离、是否遗漏必要实现。
2. 异常分支：nil/空值、非法枚举、超时/负值、部分失败后的清理、错误上下文、资源释放。
3. 重复代码：逻辑、常量、转换、校验是否重复，是否值得抽取。
4. 函数命名：是否准确表达行为，是否与同包风格一致，是否存在名实不符。
5. 注释与代码一致：注释必须自包含，不引用设计文档编号；改名、改行为后注释是否同步。
6. 可读性与圈复杂度：函数是否过长、分支是否过多；即使复杂度固有，也要评估能否拆成更小的函数。
7. 空行与排版：用空行分隔不同逻辑阶段（参数解析、加载/校验、模式分支、资源创建、清理/返回）；空行应体现意图变化，不要机械空行；同类函数保持一致；注释解释独立阶段时，注释前通常留空行；空行不能替代必要的函数拆分。
8. 重构与一致性：实现是否符合项目既有约定，是否存在不必要的抽象或过度拆分，是否破坏既有 API/配置兼容性。
9. 验证：`go build` / `go vet` / 相关测试 / `gofmt` / 范围内新增的 lint 问题。

## 输出格式

- 结论：整体质量，是否存在 P0/P1。
- 发现：按 P0/P1/P2/P3 排序，每条给 `file:line`、问题、影响、建议。
- 修复建议：区分“建议修改”和“可选优化”，并给出优先级。
- 验证结果：列出实际运行的命令和结果；未运行的要说明原因。
