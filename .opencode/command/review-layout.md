---
description: Review the layout of existing code: declaration order, method grouping, file cohesion, and readability.
---

Review 指定范围的已有代码布局（不是 diff）。不要修改代码；只做评审。

Target：$ARGUMENTS

如果 Target 为空，先询问用户要评审的文件/目录/包，不要默认扫描整个 repository。

## 范围

- 只评审指定文件/包；需要判断调用关系时，可以查看直接依赖和直接调用方。
- 不把范围外的历史问题混入结论；必须提及时标注“范围外”。
- 不以个人偏好强行重排；以 Go 社区惯例和本仓库现有风格为准，规则冲突时说明取舍。

## 重点评审布局

1. 类型、常量、变量、接口、方法、包级函数的排列是否符合阅读顺序。
2. 每个 receiver 的方法是否紧邻其类型并集中放置；同一类型的方法不要被包级函数打断。
3. 包级函数是否集中放置；导出 API 与内部 helper 的边界是否清楚。
4. 文件拆分是否合理：是否存在“一个工具函数一个文件”的过度拆分，是否存在职责混杂的大文件。
5. 文件名是否准确表达内容，是否与同包其他文件命名一致。
6. import 分组、常量/var 块、声明顺序是否清晰。
7. 空行是否用于表达逻辑阶段变化，而不是机械填充；阶段之间是否易读。
8. 注释是否紧邻对应声明，doc comment 是否以声明的名字开头，是否与代码一致。
9. 是否存在因布局导致的重复、难查找、难维护问题。
10. 判断是否值得调整；不要为了“整齐”制造无意义 diff。

## 输出格式

- 结论：整体布局质量，是否建议调整。
- 发现：按 P0/P1/P2/P3 排序，每条给出 `file:line`、问题、影响、建议。
- 建议布局：用简短大纲说明推荐的声明/方法/函数顺序，或推荐的文件拆分方式。
- 可选优化：明确哪些只是风格偏好，不必修改。
- 验证：如果只是 review，说明未运行修改后的验证；如果评审中发现必须调整，列出建议运行的 `go build` / `go vet` / `go test` / `gofmt` / lint 命令。

## 注意

- 不要仅按字母或机械顺序排列；按“类型 → 该类型的方法 → 相关包级函数/构造器”的阅读顺序判断。
- 方法多时优先保证同一类型的方法连续，而不是把所有导出函数放最前面。
- 如果一个文件只有一个很小的 helper，优先考虑并入相关领域文件，而不是单独建文件。
- 布局建议必须保持行为、API 和配置兼容性不变。
